# App Store Screenshots

Turn the app's supported value into a readable visual story. Keep the reusable method here; keep each app's audience, claims, visual identity, and accepted decisions with that app.

## Match the request

Dedicated product-page headers and search-results creative assets belong to `app-store-creative-assets` when installed. A screenshot gallery that also appears in search stays here. For a mixed request, apply the appropriate workflow to each deliverable; this skill remains usable on its own.

- **Review or discuss:** inspect the supplied set and resources, explain the most consequential problems, and propose concrete alternatives. Findings can stay in the response; do not edit files or render unless requested. Respect another session's ownership of active assets.
- **Produce:** carry authorized work through rendering, visual inspection, and a reviewable delivery. Establish a representative composition before multiplying it; this is a working method, not an extra approval gate.
- **Revise:** preserve accepted copy, order, framing, and branding except where the requested change requires an adjustment. Refresh dependent exports, previews, and packages together.
- Creating artwork does not authorize upload, metadata changes, submission, or publication. Reuse explicit authorization already given and follow the project's release process.

## Ground the story

Read applicable repository instructions and the app profile or equivalent product brief before writing copy. If neither exists, assemble a provisional brief from supplied product evidence and ask only about material unknowns. Inspect current product and release evidence, authentic captures, existing artwork, and the user's referenced guides. Read app source where a claim or capture route needs clarification.

For production or requested documentation, record audience, desired outcome, ordered headlines, the supporting screen for each headline, and claim limits. Reuse an existing story or manifest rather than adding a second source of truth. Implementation, capture, and public availability are separate facts.

Treat practitioner examples and conversion figures as attributed observations, not expected results for this app. Recheck current Apple constraints when needed; [review and delivery guidance](references/review-and-delivery.md) links the primary sources. Do not turn word counts, layout ratios, or a five-frame example into mandatory rules.

## Write before laying out

Write one plain-language audience outcome, then draft a sequence in which each frame adds a reason to use the app. Give the opening frames the clearest explanation of its distinctive value.

- A useful starting sequence is recognition or outcome → how the app helps → a concern or product demonstration → supporting benefits. Change the order and count to suit the app; never invent social proof to fill a slot.
- Give each frame one idea. Start with a short headline, roughly eight words or fewer, then judge meaning and rendered legibility rather than counting words mechanically.
- Prefer concrete words that match the action. If a screen offers skipping a step, “Choose what to skip” is clearer than “Choose what can wait,” which implies postponement. Preserve distinctions between suggestions and automatic changes.
- Read the headlines alone, in order. They should explain a useful change without the UI. Then check that each real screen actually supports its headline. Accuracy alone is not persuasive; persuasive wording still needs evidence.
- Prepare alternatives only where a decision or experiment needs them. Do not force a new caption set for a small accepted edit.

## Capture real runtime UI

Finished App Store artwork must use screenshots captured from the running app on a simulator or device. SwiftUI snapshot-test goldens, `ImageRenderer` output, and windowless reference renders are design references, even when they use real app view code. They can omit system chrome and replace Liquid Glass with plain fills. A successful snapshot test or source-code comparison does not establish runtime appearance.

Before acquiring or accepting production captures, follow [runtime capture guidance](references/runtime-capture.md). Use the intended build, normal rendering path, requested appearance, and a ready app state. Inspect one raw runtime capture for authentic materials and system UI before capturing or composing the whole set. Existing runtime captures may be reused when their provenance and visible appearance match the intended release; a request for fresh captures requires a new runtime capture.

If runtime capture fails, keep the affected artwork explicitly incomplete and report the missing capture. Continue independent preparation and retry through a concrete supported recovery path. Do not substitute snapshot references, rename them as screenshots, or upload a fallback set as the completed request. An explicitly requested layout mockup can use clearly marked references; it is not the finished screenshot set.

## Compose from authentic screens

Inspect source images before placing them. Use the app's real icon, licensed fonts, and established visual identity. Never generate, redraw, recolor, or retouch software UI to match the headline. If a needed state is missing, obtain an authorized capture, select another supported benefit, or identify the gap in the review draft.

Follow the user's framing preference. When no direction exists, a short headline above one complete device containing a full app screen is a useful starting layout, not an Apple requirement or a proven conversion winner.

If full screens and complete devices are requested, retain the whole captured viewport at its original aspect ratio, keep the phone within the canvas, and avoid floating excerpts or duplicated fragments. Natural scroll clipping already present in the capture does not justify reconstructing unseen content. Any alternative crop should be deliberate and consistent with the agreed treatment.

Keep editorial copy outside the UI and hardware separate from software. Use authentic captures for each requested appearance; never simulate dark mode by inverting or recoloring a light capture. Read the [capture and framing checks](references/review-and-delivery.md#capture-and-framing) when source images omit system chrome or come from reference renders.

Use consistent type, palette, headline position, phone scale, and spacing across the set. Keep the main message readable at thumbnail size; enlarged UI fragments are not the default remedy for a weak headline. Reuse the established renderer or editor when suitable, and respect an explicitly requested authoring tool.

## Verify and deliver

For production, follow [review and delivery guidance](references/review-and-delivery.md): verify source provenance, inspect every distinct composition at full size, inspect the sequence and small thumbnails, check required export variants, and verify the delivery package. Automated geometry and file checks do not establish visual quality or conversion improvement.

Keep copy and order in one source used by the artwork, review gallery, accessible descriptions, and delivery notes. A caption edit must not leave stale text or exports in the package. Keep approved exports intact unless the user authorized their revision.

Deliver the review location, finished outputs, relevant checks, and any material capture or release limitations. Follow the repository's handoff and sync conventions. Distinguish a produced draft from approved artwork and an uploaded asset from a live listing. If testing conversion is requested, define the treatment and success measure; elapsed time or a cleaner design alone is not evidence of a lift.
